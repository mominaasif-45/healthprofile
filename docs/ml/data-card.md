# Data card: synthetic appointment no-show dataset

> **Educational prototype. Every row is invented.** No real people, no real clinic, no real patient data,
> and nothing taken from HealthProfile member profiles. The outcome comes from rules **we wrote**, so any
> model score measured on this data shows that the *method* works. It says **nothing** about how
> well anything would predict no-shows in a real clinic.

## Provenance

* **Who made it:** the generator script in this repository. It was written for Week 3 of the HealthProfile
  internship project (November 2026).
* **How:** `numpy.random.default_rng(seed)` draws every value. The same seed and settings always give the
  same file. The draws always happen in the same order, so changing `--noise` changes only `no_show`,
  never the appointments.
* **Nothing was collected, scraped or downloaded.** No external dataset was used as a template.
* **Pinned versions:** numpy and pandas are pinned in `backend/requirements.txt`. A different numpy
  version may draw different random numbers from the same seed. The checksum test catches this.

## Intended use

* **For:** practising an ML workflow (analysis, missing values, leakage-safe splitting, model comparison,
  per-group metrics, a reproducible pipeline and an API) in a teaching project.
* **Not for:** making decisions about real people or appointments. Not for drawing conclusions about any
  real age group, booking channel or neighbourhood. Not for clinical or medical use of any kind.

## Schema

Every feature is something a clinic would know **when the appointment is booked**. Nothing is recorded after
the visit, such as check-in time, arrival or cancellation reason. Columns like that would leak the answer.

| Column | Type | Values | Blank? | Meaning (all fictional) |
|---|---|---|---|---|
| `appointment_id` | text | `A00001` … `A06000` | never | Row identifier. **Not a feature** |
| `lead_time_days` | integer | 0–90 (median 8) | never | Days between booking and appointment |
| `weekday` | text | `mon` … `sat` | never | Day of the appointment |
| `hour` | integer | 8–17 | never | Start hour |
| `visit_type` | text | `new_visit`, `follow_up`, `routine_checkup`, `wellness_class` | never | Kind of appointment |
| `booking_channel` | text | `online`, `phone`, `in_person` | never | How it was booked |
| `reminder_sent` | text | `yes`, `no` | 6.1% | Whether a reminder was sent |
| `prior_visits` | integer | 0–20 (max seen 11) | 3.0% | Earlier appointments for this person |
| `prior_no_shows` | integer | 0 to `prior_visits` | 3.0% (same rows as `prior_visits`) | Earlier missed appointments |
| `distance_band` | text | `under_5km`, `5_15km`, `15_30km`, `over_30km` | 7.9% | Rough travel distance |
| `age_band` | text | `18-24`, `25-34`, `35-44`, `45-54`, `55-64`, `65+` | 4.0% | Age group |
| `no_show` | integer | `1` = missed, `0` = attended | never | **The outcome (label)** |

## How the outcome is made

> **The differences below are arbitrary choices.** We made up every number, including the ones for
> age band, booking channel, distance and weekday. They exist only to give the models a pattern to learn
> and to give the per-group checks (Phases 3 and 7) something to find. They are **not claims about real
> people or populations**, and nothing about real behaviour should be read into them.

For each row the generator builds a **risk score** by adding up the numbers below. Then:

1. it adds random **noise**: `noise × a random number from a bell curve` (`noise = 1.0` here);
2. it adds a constant, chosen automatically so the average no-show chance is 20%;
3. it turns the score into a probability (logistic function) and flips a seeded weighted coin.

| Part of the rule | Adds to the risk score |
|---|---|
| Lead time | +0.03 per day, counted up to 60 days |
| Earlier no-shows | +2.0 × `prior_no_shows / (prior_visits + 1)` |
| Reminder sent | −0.8 |
| Weekday | `mon` +0.25, `fri` +0.30, `sat` +0.15, others 0 |
| Hour | 8:00 +0.20, 16:00 and 17:00 +0.15, others 0 |
| Visit type | `new_visit` +0.30, `routine_checkup` +0.10, `wellness_class` +0.40, `follow_up` 0 |
| Booking channel | `online` +0.20, `in_person` −0.30, `phone` 0 |
| Distance band | `5_15km` +0.15, `15_30km` +0.35, `over_30km` +0.60, `under_5km` 0 |
| Age band | `18-24` +0.45, `25-34` +0.30, `35-44` +0.10, `55-64` −0.10, `65+` +0.15, `45-54` 0 |

The rule uses the **true** values, before any are blanked out (see [Missing values](#missing-values)).
Reminders are sent more often for online bookings (80%) than for phone (60%) or in-person (55%) bookings.

## The noise setting and the best possible score

**Noise** is extra randomness that the columns cannot explain. Real outcomes are messy. People miss
appointments for reasons no dataset records. Raising `--noise` (0 to 5) makes this data messier.

**Best possible score, in plain words.** We wrote the rule, so we can ask: *if a model knew the rule
exactly, how well could it rank the appointments?* We measure that "perfect-knowledge" ranking with
ROC-AUC, a score from 0.5 (guessing) to 1.0 (always ranks every no-show above every attended visit).
On this file it is **0.657**. No honest model can beat that, because neither the noise nor the final
coin flip can be predicted from the columns. If a model in Phase 3 scores **at or above 0.657**, or anything
near-perfect, something is wrong (most likely leakage), and we will stop and investigate.

| `--noise` | 0 | 0.5 | 1.0 (used) | 2 | 3 |
|---|---|---|---|---|---|
| No-show rate | 20.8% | 20.3% | 20.8% | 20.9% | 20.2% |
| Best possible ROC-AUC | 0.671 | 0.672 | 0.657 | 0.625 | 0.600 |

Even with zero noise the ceiling is only about 0.67, because the final coin flip already adds a lot of
randomness. Between noise 0 and 0.5 the two numbers are within measurement wobble. The tests only check
the clear trend (0 > 1 > 3).

## Missing values

Blanks are added **after** the outcome is decided, so whether a cell is blank never depends on `no_show`.

| Column | Blank rate | Pattern |
|---|---|---|
| `reminder_sent` | 6.1% | Completely at random |
| `prior_visits` + `prior_no_shows` | 3.0% | Completely at random, always blank **together** |
| `age_band` | 4.0% | Completely at random |
| `distance_band` | 7.9% | **Depends on another column:** 13.8% for phone bookings vs 4.7% otherwise |

Real missing data is rarely random, so the distance blanks deliberately depend on the booking channel.
A model could learn "blank distance" partly as "booked by phone". Phase 2 handles blanks inside the
pipeline, learning only from the training split, and adds "was missing" indicators.

## Class imbalance

Only **20.8%** of rows are no-shows. A model that always says "will attend" is right 79% of the time and
useless. Accuracy is therefore a misleading metric here. Phase 3 reports PR-AUC, recall, precision and F1 for
the no-show class, plus balanced accuracy, and compares every model against that "always attend" baseline.

## Built-in bias and group sizes

The bias in this dataset is **ours, on purpose**, as described above. Phases 3 and 7 check whether
models treat groups differently. Observed no-show rates in the file:

| Age band | Rows | No-show rate | | Booking channel | Rows | No-show rate | | Distance band | Rows | No-show rate |
|---|---|---|---|---|---|---|---|---|---|---|
| 18-24 | 785 | 23.9% | | online | 3,224 | 20.8% | | under_5km | 1,919 | 18.2% |
| 25-34 | 1,376 | 20.9% | | phone | 2,131 | 21.4% | | 5_15km | 1,953 | 20.3% |
| 35-44 | 1,235 | 20.4% | | in_person | 645 | 18.9% | | 15_30km | 1,087 | 22.5% |
| 45-54 | 1,008 | 19.4% | | | | | | over_30km | 567 | 27.2% |
| 55-64 | 804 | 19.7% | | | | | | (blank) | 474 | 21.7% |
| 65+ | 552 | 22.1% | | | | | | | | |
| (blank) | 240 | 18.8% | | | | | | | | |

Things to notice:

* **Small groups.** `65+` (552 rows), `over_30km` (567) and `in_person` (645) are small. In a 15% test split
  they have under 100 rows each, so their metrics will be noisy. Phase 3 reports group sizes next to every
  per-group metric.
* **Raw rates can hide the rule.** The rule gives `online` bookings +0.20 risk compared with `phone`.
  Yet online bookings have a slightly *lower* no-show rate (20.8% vs 21.4%), because online bookings get
  more reminders, which lower risk. This is a simple example of **confounding**: looking at one column at a
  time can point the wrong way.
* **Reminder** is the strongest single signal: 28.3% no-shows without a reminder vs 17.7% with one.

## Leakage safeguards

* Only booking-time columns. The rule's risk score and true probability are **never** written to the CSV.
* `appointment_id` is an identifier and must not be used as a feature. Phase 2 drops it.
* Tests check that no column name suggests post-visit or rule information, and that no category with at
  least 30 rows is 0% or 100% no-shows (no hidden copy of the label).
* Splitting (Phase 2) happens **before** any preprocessing is fitted.

## Limitations

* **Synthetic data follows the rules we wrote.** A model can only rediscover those rules. Its scores
  measure how well the method recovers a pattern we planted, not how well it would work on real
  appointments, which have many more causes and much messier data.
* **Scores here will look better than real life in one way and worse in another.** The pattern is clean
  and stable: there is no drift over time and the rule never changes. But the signal is deliberately modest,
  with a ceiling of 0.657 ROC-AUC.
* The columns are a small, hand-picked set. Real no-show behaviour depends on things not modelled here, such
  as transport, work, caring duties, weather and illness.
* Each row is independent. There are no repeat patients, no seasons and no clinic-to-clinic differences.
* Group differences are **invented** (see the warning above), so per-group results show how to *measure*
  bias, not what real bias looks like.

## Reproduce and verify

From `backend/` with the venv active:

```bash
python -m ml.data.generate --seed 42 --rows 6000 --noise 1.0   # rewrites the CSV and metadata
python -m pytest tests/test_ml_data.py                          # 38 tests, including the checksum check
```

`git` may check the CSV out with Windows line endings (`core.autocrlf=true`). The checksum is computed
over the text with line endings normalised to `\n`, so it matches on every platform.
